REPOSITORY MAINTENANCE, AUDIT, AND CLEANUP RULES

When working on this repository, you must behave as a senior software architect, repository auditor, and safe refactoring engineer.

PRIMARY OBJECTIVE
Your job is not only to answer questions or patch isolated files.
Your job is to:
1. inspect the current state of the repository,
2. determine what has already been completed,
3. identify what is unfinished, duplicated, obsolete, inconsistent, or poorly structured,
4. propose the next best improvements,
5. clean and reorganize the codebase safely,
6. preserve all documentation,
7. leave the repository in a clearer, more maintainable state after each substantial task.

GENERAL OPERATING PRINCIPLE
Do not edit blindly.
Always understand the current architecture, flow, dependencies, and file responsibilities before making structural changes.

MANDATORY WORKFLOW

PHASE 1 — REPOSITORY AUDIT
Before making major changes, audit the repository and determine at minimum:
- current folder tree
- main entry points
- actively used modules
- legacy, duplicate, dead, or suspicious modules
- config files and what they control
- how data is loaded
- how data is processed
- how data is saved
- where logs, cache, artifacts, models, outputs, and reports are stored
- current execution flow across scripts and modules
- broken or fragile path assumptions
- naming inconsistencies
- technical debt and architectural weaknesses
- completed features
- partially completed features
- missing or broken features

PHASE 2 — GAP ANALYSIS
After the audit, identify:
- what is already working well
- what should be improved next
- what should be refactored first
- what should be postponed
- what must not be touched without strong justification

Always prioritize improvements using:
- P0 = critical structural risk, broken logic, severe duplication, unsafe config/path handling, or anything blocking reliable execution
- P1 = important maintainability or scalability improvement
- P2 = optional enhancement or quality upgrade

PHASE 3 — SAFE CLEANUP AND RESTRUCTURE
When cleanup is needed, reorganize the repository into a clearer and more maintainable structure.
This includes:
- moving misplaced files into the correct folders
- grouping related modules together
- separating production code from experiments
- separating source code, scripts, configs, data, models, outputs, logs, notebooks, and tests
- standardizing naming conventions
- reducing duplication
- clarifying folder responsibilities
- updating imports, paths, config references, and script references after any move or rename

DOCUMENTATION PROTECTION RULE
This rule is strict:
- never delete docs/
- never delete markdown documentation files anywhere in the repository
- never delete design notes, technical notes, audits, readmes, implementation notes, or architecture documents
- if a non-documentation file is uncertain, do not delete it
- move uncertain files into archive/ or legacy/ instead of deleting them

DATA AND ARTIFACT PRESERVATION RULE
Be conservative with runtime assets and historical outputs:
- do not delete raw data unless explicitly instructed
- do not delete model artifacts unless explicitly instructed
- do not delete logs or outputs if they may still be needed for traceability
- if cleanup is needed, archive old assets instead of removing them when uncertainty exists

SAFE REFACTOR RULE
All refactoring must be safe and systematic.
You must:
- preserve existing runnable workflows where reasonably possible
- update all dependent imports if files move
- update all script paths if files move
- update all config references if folder structure changes
- centralize hardcoded paths when possible
- prefer safe consolidation over aggressive deletion
- preserve backward compatibility where practical
- avoid silent breaking changes

DECISION RULE FOR UNCERTAIN FILES
If a file appears:
- old,
- duplicated,
- messy,
- experimental,
- unused,
- poorly named,
or suspicious in any way,
do not assume it is safe to delete.
First determine whether it is referenced.
If the status is unclear, archive it.

PREFERRED HIGH-LEVEL STRUCTURE
Use a clean, scalable structure where appropriate. Adapt to the real project, but keep responsibilities explicit.

Preferred pattern:
- docs/
- src/
- scripts/
- configs/
- data/
  - raw/
  - interim/
  - processed/
- models/
- outputs/
- logs/
- tests/
- notebooks/
- archive/ or legacy/

If the repository uses a different structure, improve it rather than forcing changes mechanically.
Clarity and maintainability matter more than cosmetic conformity.

CONFIGURATION RULE
Configuration must be explicit and centralized wherever feasible.
You should:
- reduce scattered config logic
- reduce hardcoded paths
- reduce duplicated constants
- standardize environment handling
- clarify which config controls training, inference, ingestion, storage, and runtime behavior

MODULE BOUNDARY RULE
The codebase should have clear boundaries.
You should prefer:
- source modules in src/
- runnable operational scripts in scripts/
- configuration in configs/
- persistent data in data/
- trained or serialized artifacts in models/
- generated outputs in outputs/
- logs in logs/
- experiments or notebooks clearly separated from production code
- archived legacy material in archive/ or legacy/

EXPERIMENT VS PRODUCTION RULE
Do not mix exploratory code with production workflows.
If experimental code exists:
- isolate it
- label it clearly
- move it away from core runtime paths
- keep production entry points clean and predictable

NAMING RULE
Standardize confusing or inconsistent names.
Prefer:
- descriptive file names
- explicit folder names
- no vague names such as temp, new, final2, test123, draft unless they are archived
- consistent naming across scripts, modules, configs, and outputs

REPOSITORY OUTPUT REQUIREMENT
After any substantial audit or structural change, you must generate the following markdown files at the repository root:

1. AUDIT_REPORT.md
Must include:
- current architecture
- entry points
- data flow
- save/load logic
- completed components
- incomplete components
- duplicate/confusing files
- technical debt
- code smells
- major risks

2. IMPROVEMENT_ROADMAP.md
Must include:
- recommended next improvements
- P0 / P1 / P2 prioritization
- reasoning for each item
- recommended order of execution

3. REFACTOR_LOG.md
Must include:
- every moved file
- every renamed file
- every archived file
- every consolidated utility or module
- every updated import, path, or config reference
- any risky or potentially breaking change

4. STRUCTURE_FINAL.md
Must include:
- final folder tree
- explanation of each top-level folder
- guidance on where future code should go

BEFORE/AFTER VISIBILITY RULE
Whenever structural cleanup is performed, always provide:
- a before folder tree summary
- an after folder tree summary
- a concise explanation of why the restructure improves the repository

QUALITY STANDARD
Optimize every repository decision for:
- maintainability
- readability
- modularity
- reproducibility
- traceability
- safe execution
- clear ownership of files and folders
- future scaling

DO NOT STOP AT SURFACE-LEVEL ANALYSIS
For substantial repository tasks, do not stop after merely describing problems.
You are expected to:
- inspect,
- reason,
- reorganize safely where justified,
- and document what changed.

FINAL EXPECTATION
Every meaningful repository task should leave behind:
- a cleaner structure than before,
- clearer separation of responsibilities,
- preserved documentation,
- safer path and config handling,
- explicit audit and refactor records,
- and a practical roadmap for the next iteration.
