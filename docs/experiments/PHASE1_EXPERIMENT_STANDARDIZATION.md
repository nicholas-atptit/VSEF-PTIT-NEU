  ## Phase 1 Objective

  Phase 1 standardizes VSEF experiment execution around one principle:

  ```text
  CONFIG IN -> ORCHESTRATED RUN -> STANDARD ARTIFACTS OUT
  ```

  The goal is not to expand model ambition. The goal is to make every experiment
  run reproducible, comparable, and auditable through a YAML config, resolved
  config copy, logs, manifest, predictions, metrics, and summary.

  ## Relation to Phase 0 Governance Freeze

  Phase 1 respects the Phase 0 VSEF v1 governance freeze:

  - Supported forecasting models remain SARIMAX, ETS, XGBoost, LightGBM, LSTM,
    BiLSTM, and Stacking.
  - Baselines are comparison evidence only and are not official forecasting
    models in the Phase 0 model registry.
  - The official provider remains `vnstock_data`.
  - Frequency remains daily OHLCV.
  - Diagnostic outputs must not be represented as BUY / SELL / HOLD advice.
  - No live trading, broker execution, autonomous LLM decision agents, portfolio
    allocation logic, or new data provider is introduced by Phase 1.

  ## ExperimentOrchestrator Role

  `src/engine/experiment_orchestrator.py` provides `ExperimentOrchestrator`.

  The orchestrator:

  - Loads one YAML config.
  - Validates required config fields and Phase 0 boundaries.
  - Creates `outputs/experiments/{experiment_id}/`.
  - Saves `config/original_config.yaml` and `config/resolved_config.yaml`.
  - Executes ticker/horizon runs sequentially.
  - Runs configured supported models and configured baselines.
  - Writes predictions, metrics, manifest, logs, and summary.
  - Records errors without faking successful results.

  The orchestrator does not hardcode ticker, date, horizon, model, baseline, risk,
  or experiment ID choices. Those values come from config.

  ## Config Schema

  Configs live under `configs/experiments/`.

  Required sections:

  - `experiment`: ID, name, description, phase, owner, creation date, seed.
  - `data`: provider, frequency, universe, date window, required OHLCV schema.
  - `target`: target column, task type, horizons.
  - `features`: enabled flag and feature-set names.
  - `models`: enabled flag, supported model list, optional model params.
  - `baselines`: enabled flag, baseline list, optional baseline params.
  - `evaluation`: method, train/test dates, metric names.
  - `risk`: enabled flag and methods, currently documentation/config evidence only.
  - `outputs`: output root and artifact save flags.
  - `runtime`: fail-fast behavior, max workers, log level.

  Validation rules:

  - `data.provider` must be `vnstock_data`.
  - `data.frequency` must be `daily`.
  - Models must belong to the Phase 0 frozen model registry.
  - Baselines must belong to the Phase 1 baseline registry.
  - Horizons must be positive integers.
  - Dates must be valid ISO dates.
  - `outputs.root_dir` must be under `outputs/experiments` unless explicitly
    overridden for tests.
  - `experiment.id` is used in output folder naming.

  See `configs/experiments/schema_example.yaml`.

  ## Output Folder Contract

  Each run writes to:

  ```text
  outputs/experiments/{experiment_id}/
    config/
      original_config.yaml
      resolved_config.yaml
    manifests/
      run_manifest.json
    logs/
      run.log
      errors.log
    metrics/
      metrics.csv
      metrics_summary.json
    predictions/
      predictions.csv
      baseline_predictions.csv
      model_predictions.csv
    artifacts/
      forecast_summary.csv
      model_consensus_summary.csv
      model_health_summary.csv
      risk_summary.csv
      strategy_metrics.csv
      decision_lane_candidates.csv
      analysis_packets.jsonl
    charts/
      .gitkeep or generated charts
    reports/
      summary.md
  ```

  The current Phase 1 runtime always writes config, manifest, logs, predictions,
  metrics, and summary where possible. It does not fake optional artifacts. If an
  expected artifact is not generated by the current runtime path, the manifest
  records a warning and the summary explains that the artifact was not generated.

  ## Metrics Engine

  `src/ml/evaluation/metrics_engine.py` provides `MetricsEngine`.

  It writes one standardized long-form metrics table for models and baselines:

  - `experiment_id`
  - `run_id`
  - `ticker`
  - `horizon`
  - `model_name`
  - `model_type`
  - `metric_group`
  - `metric_name`
  - `metric_value`
  - `sample_size`
  - `start_date`
  - `end_date`
  - `notes`

  Metric groups include:

  - Forecast metrics: MAE, RMSE, MAPE where numerically safe, directional
    accuracy.
  - Decision diagnostics: signal accuracy when signal labels exist,
    coverage count, prediction count.
  - Risk metrics: realized volatility when returns exist, max drawdown when an
    equity curve exists, VaR/CVaR passthrough when already present.
  - Stability metrics: prediction standard deviation, error standard deviation,
    missing prediction rate.

  Metrics that cannot be computed are written as null with an explanatory note.

  ## Baseline Registry

  `src/ml/baselines/baseline_registry.py` provides `BaselineRegistry`.

  Registered baselines:

  - `persistence`
  - `zero_return`
  - `random_direction`
  - `moving_average_rule`

  Baselines are deterministic when the experiment seed is fixed. They appear
  beside main models in the same `metrics/metrics.csv` table with
  `model_type=baseline`.

  ## Smoke Experiment Design

  `configs/experiments/EXP-SMOKE-001.yaml` is the Phase 1 smoke config.

  Design:

  - Ticker: `FPT`
  - Horizon: `1`
  - Models: `ets`, `sarimax`
  - Baselines: `persistence`, `zero_return`
  - Provider: `vnstock_data`
  - Frequency: daily OHLCV
  - Evaluation: fixed chronological train/test split
  - Runtime: sequential, `fail_fast=false`

  The smoke run checks config loading, validation, output folder creation,
  resolved config saving, manifest writing, metrics writing, baseline/model
  metrics in the same table, and graceful failure recording if provider or model
  runtime is unavailable.

  ## Reproducibility Experiment Design

  `configs/experiments/EXP-CONFIG-001.yaml` is the config reproducibility config.

  Design:

  - Run the same config twice.
  - Compare `resolved_config.yaml`.
  - Compare `metrics.csv` schema.
  - Compare `run_manifest.json` schema.
  - Compare artifact presence.

  The helper script `scripts/compare_experiment_runs.py` compares two output
  folders:

  ```powershell
  python scripts/compare_experiment_runs.py --left outputs/experiments/archive/EXP-CONFIG-001-RUN-A --right outputs/experiments/archive/EXP-CONFIG-001-RUN-B
  ```

  For a strict two-run comparison, copy or archive the first output folder before
  starting the second run, then pass the two folder paths to the comparison
  script. For example, preserve the first run as `EXP-CONFIG-001-RUN-A`, preserve
  the second run as `EXP-CONFIG-001-RUN-B`, and compare those archived folders.
  Identical stochastic results are not required unless the full runtime path is
  deterministic with a fixed seed.

  ## Troubleshooting

  ### vnstock_data import failure

  If `EXP-SMOKE-001` fails with `vnstock_data_not_installed` or
  `provider_import_failed`, treat it as an environment/interpreter issue first.
  The Phase 0 data policy still requires `vnstock_data`; do not replace it with
  another provider.

  The common cause is running `scripts/run_experiment.py` with the wrong Python
  interpreter. Check the active interpreter and provider import path:

  ```powershell
  C:\Users\luong\.venv\Scripts\python.exe -c "import sys; print(sys.executable); import vnstock_data; print(vnstock_data.__file__)"
  ```

  Run the smoke with the project environment:

  ```powershell
  C:\Users\luong\.venv\Scripts\python.exe scripts\run_experiment.py --config configs\experiments\EXP-SMOKE-001.yaml
  ```

  When provider import fails, the orchestrator records `sys.executable`,
  `sys.version`, provider name, and the import error message in
  `manifests/run_manifest.json`, `logs/errors.log`, and `reports/summary.md`.
  Failure evidence is valid environment evidence, but it is not successful model
  or baseline performance evidence.

  ### Missing model dependency: statsmodels

  If `EXP-SMOKE-001` reaches `vnstock_data` successfully but ETS or SARIMAX fail
  with `ModuleNotFoundError: No module named 'statsmodels'`, install
  `statsmodels` in the same project venv used for the smoke run:

  ```powershell
  C:\Users\luong\.venv\Scripts\python.exe -m pip install statsmodels
  ```

  Verify the dependency in that venv:

  ```powershell
  C:\Users\luong\.venv\Scripts\python.exe -c "import statsmodels.api as sm; print(sm.__version__)"
  ```

  Rerun the smoke after dependency verification:

  ```powershell
  C:\Users\luong\.venv\Scripts\python.exe scripts\run_experiment.py --config configs\experiments\EXP-SMOKE-001.yaml
  ```

  ## Acceptance Criteria

  - [x] A single YAML config can start an experiment run.
  - [x] ExperimentOrchestrator does not hardcode ticker/model/date/horizon choices.
  - [x] Output folder follows `outputs/experiments/EXP-*` structure.
  - [x] Each run saves config, manifest, metrics, logs, and summary where possible.
  - [x] Baselines appear in the same metrics table as main models.
  - [x] Metrics engine computes forecast metrics consistently.
  - [x] Baseline registry includes persistence, zero_return, random_direction, and moving_average_rule.
  - [x] Smoke experiment can run end-to-end or fails with a clear manifest and error log.
  - [x] Config reproducibility experiment has a defined comparison method.
  - [x] No fake evidence is created.
  - [x] No Phase 0 governance boundary is violated.

  ## Known Limitations

  - ExperimentOrchestrator v1 executes sequentially even if `runtime.max_workers`
    is greater than one.
  - Provider access depends on the local `vnstock_data` runtime and network/API
    availability.
  - Optional expected artifacts are not faked when the current runtime path does
    not generate them.
  - Model failures are recorded in errors and manifests. They do not imply a
    successful model-quality claim.
  - The comparison helper checks reproducibility structure, not statistical
    equivalence.

  ## Future Work Deferred To Later Phases

  - Parallel experiment execution.
  - Broader artifact generation from the governed Quant Core path.
  - Rich chart generation.
  - Cross-run experiment registry.
  - Portfolio allocation, broker execution, live trading, and autonomous agents
